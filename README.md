# 行迹 · 智能行程规划

> 输入「去哪儿、玩几天」，得到一份**带攻略出处、可拖拽调整、可导出手机日历、可一键分享**的行程。

一个面向中文旅行场景的智能行程规划系统。后端 FastAPI + 自研混合检索，前端 Vue3 + TypeScript。

---

## 它解决什么问题

市面上多数「AI 旅行规划」Demo 止步于「调一次大模型，吐一段文本」。文本拿去没用——**不知道去哪、几点去、住哪、花多少、怎么带走**。

行迹把这条链路做完整了：

| 环节 | 做法 |
|---|---|
| 能去哪 | 全国任意城市可搜索（高德补全），其中 10 座有完整本地攻略 |
| 怎么去 | 「出发地 → 目的地」路线规划，按里程/时长判断**要不要中途停**，并在路线走廊里算出**顺路且值得停**的城市 |
| 推荐从哪来 | **候选池**：本地攻略库（混合检索 BM25 + 字符 n-gram，可选向量与精排）**＋** 高德 POI 宽召回，两者合并后按偏好排序 |
| 谁来编排 | **大模型从候选池里选点、定主题、写推荐理由**；超时/返回不合格/未配 Key 时自动退回规则生成，功能不中断 |
| 凭什么信它 | 大模型选的每一个地名都**回池子逐个核对**，编造的一律丢弃；每条安排标注**出处**（本地攻略 / 高德POI） |
| 怎么带上路 | 导出 **ICS 日历**，直接进手机日程 |
| 怎么给别人看 | 生成**只读分享链接**，token 可撤销 |
| 临出门 | 按城市/天数/季节自动生成**打包清单** |

## 功能一览

### 核心
- **多城市串联**：按顺序串联最多 6 个城市，天数自动分配（3 城 8 天 → 3/3/2）
- **偏好驱动检索**：勾选「亲子/摄影/美食」会改变检索排序，而不是摆设
- **逐日行程**：每天含景点、餐食、住宿区域与当日主题
- **预算拆分**：住宿 / 餐饮 / 市内交通 / 门票 / 城际交通，按城市消费水平估算

### 四个特色能力
1. **行程拖拽调整** — 天内任意拖拽重排（限天内，防止拖出「人在成都，住宿在大理」）
2. **ICS 日历导出** — RFC 5545 合规：CRLF 换行、75 字节折行、特殊字符转义、全天事件开区间
3. **只读分享链接** — 随机 token，删除行程时分享链接同步失效，不留悬空引用
4. **打包清单** — 规则生成（非 LLM），按目的地标签与出发季节补齐，结果可复现

### 高德地图集成（可选增强）
5. **全国城市搜索** — 输入即搜，结果区分「有攻略 / 仅定位」，边打边猜带键盘导航
6. **路线规划 + 中途推荐** — 出发地 → 目的地，回答「中间值不值得停、停哪儿」，可一键采纳成行程
7. **POI 候选池** — 把「某城市有什么可玩的」宽召回并落盘（一城约 130 条，30 天 TTL），供大模型选点，同时省掉重复外呼

### 大模型编排（可选增强）
8. **从候选池选点编排** — 不是「让模型自由发挥」，而是**给定候选、约束它只能在里面挑**：
   模型负责选哪几个、怎么分天、起什么主题、为什么推荐；地名必须原样照抄
9. **防幻觉靠核对，不靠提示词** — 模型返回后逐个比对候选池，不在池子里的一律丢弃；
   合规率低于 60% 则整份作废、退回规则生成
10. **降级是显式的** — 行程带 `generator` 字段（`llm` / `rule`）与降级原因，界面如实标注，
    不会把「规则生成」伪装成「大模型出品」

### 工程
- **深浅主题**：全站 CSS 变量驱动，跟随系统偏好，可手动切换并记忆
- **响应式**：移动端可用
- **106 项 pytest**：覆盖检索、清单、ICS、接口、路线走廊算法、高德降级与粒度把关、
  候选池召回与过滤、大模型拆壳/清洗/防幻觉核对/降级判定
- **端到端 UI 冒烟测试**：用 CDP 驱动真实浏览器跑完整交互路径并截图（`.tools/verify-ui.mjs`）

## 检索链路

```
用户查询
   ├─▶ ① BM25（jieba 分词）          关键词精确命中
   ├─▶ ② 字符二元组 TF-IDF 余弦      抗分词错误、抗口语化
   └─▶ ③ 向量召回（可选）            语义相近也能召回
              │
              ▼
        ④ RRF 融合  score = Σ 1/(K + rank)
              │
              ▼
        ⑤ Cross-encoder 精排（可选）
              │
              ▼
          最终 Top-K（带出处）
```

**为什么用 RRF 而不是加权求和**：BM25 分数是十几到几十，余弦是 0~1，量纲不同。加权求和要先归一化，而归一化对分布敏感、很脆。RRF 只用名次，天然免调参、免归一化。

**为什么 ①② 是必选、③⑤ 是可选**：很多 RAG 项目绑死向量库与 Embedding 模型，换台机器或下不动模型就直接跑不起来。这里保证**零重依赖也能跑出混合检索**，模型可用时再叠加。

## 路线规划：怎么判断「中间值不值得停」

问题拆成三步：

```
① 这两点多远、开多久？   高德驾车路径实测；无 Key 则直线距离 × 路网系数 ÷ 平均时速
② 值不值得中途停？      里程 > 500km 或 时长 > 6h → 建议停
③ 停哪儿？              在「路线走廊」里找顺路的已收录城市
```

**什么叫「顺路」**——把出发地→目的地拉成一条直线，衡量候选城市三个指标：

| 指标 | 含义 | 阈值 |
|---|---|---|
| 垂直距离 | 城市离这条线多远 | ≤ 130 km |
| 投影位置 | 落在全程的百分之几处 | 15% ~ 85%（贴两端的不算「中途」） |
| 绕行里程 | 绕它一下要多开多少 | ≤ 260 km |

三者同时满足才进候选，再按 `分数 = 绕行里程 − 景点数 × 12` 排序取前 2 名——**绕路越少越好，可玩内容越多越好**。

两个容易踩的坑，都已在代码里处理并写了测试：

- **绕行里程必须和基准里程同量纲。** 高德给的是**公路里程**，而球面直线距离通常**更短**。拿直线和去减公路里程，绕行会被压成 0，界面上就会出现「绕行 0 km」这种不可信的推荐。所以统一套用路网系数换算到公路尺度。
- **结论里的里程必须等于返回字段的里程。** 推荐了中途城市后，全程是「分段求和」而不是「两点直达 + 估算绕行」，两者会差出几十公里。用户会看到两个不同的「全程里程」，所以结论文本一律引用分段求和的结果。

## 高德集成：可选增强，不是硬依赖

整个地图能力遵循一条规则——**配了 Key 用真实数据，没配 Key 自动降级，功能永远完整**：

| 能力 | 有 Key | 无 Key |
|---|---|---|
| 城市搜索 | 全国任意城市 | 仅已收录的 10 座 |
| 坐标解析 | 高德地理编码 | 本地经纬度表 |
| 里程 / 时长 | 驾车路径实测 | 直线距离 × 1.28 ÷ 75km/h |
| 无攻略城市的行程素材 | 高德 POI（按分类编码检索） | 该城市当天无安排 |

结果里带 `source` 字段（`amap` / `estimate`），界面据此显示「高德实测」或「本地估算」——**降级不是静默的**。

### 两个必须拦住的坑

**坑一：高德地理编码过于宽松。** 输入「不存在的城市xyz」，它会匹配到 level=村庄 的野点，甚至返回一个地名叫「城市」的兴趣点。不拦截的后果不是报错，而是**静默生成一条从银川出发的荒谬路线**，用户还以为是自己的输入被正确识别了。

解决办法是按 `level` 把关，只接受 `省 / 市 / 区县` 三档行政区划：

```
成都        → level=市     ✓
香格里拉      → level=区县   ✓
不存在的城市xyz → level=村庄   ✗ 拒绝 → 返回 400「无法识别出发地」
火星基地      → level=兴趣点  ✗ 拒绝（出发地/目的地应该填城市，不是景点门口）
```

**坑二：搜索框里的「城市」其实是 POI。** 用输入提示接口搜城市时，返回结果里混着「成都东站停车场」这类 POI。实测发现**城市级和 POI 的 `district` 字段层数不同**：

```
城市  张家界市   district=湖南省张家界市         ← 省 + 市，两层
POI   张家界西站  district=湖南省张家界市永定区    ← 省 + 市 + 区，三层
```

所以城市级结果的 `district` **一定以城市自己的名字结尾**。再加一道「市/自治州/地区/盟」后缀白名单，把「朝阳区」这类市辖区也挡住。

### 无攻略城市怎么办

城市搜索覆盖全国，但攻略库只有 10 座。如果对没攻略的城市什么都不返回，用户会拿到一份**天天空白**的行程——这比直接报「不支持该城市」更糟，因为它看起来像是生成成功了。

所以用高德 POI 按分类编码兜底，并且**逐条标注出处**（`高德POI · 风景名胜`），让用户一眼看出内容来源不同，而不是被蒙在鼓里。

## 候选池：让大模型「有得挑」

大模型要「从候选里挑」，前提是候选**先摆出来**。v0.2 是临时查询——一次只问一个关键词，拿到三五条，候选太少，选点等于白搭。

所以拆出一层**候选池**（`poi_pool_service`）：

```
宽召回（高德，按分类翻页）          本地攻略（RAG 检索）
  景点 110000 × 2 页                  景点 / 美食 / 住宿
  景点 140000 × 1 页（带白名单）             │
  美食 050000 × 2 页                        │
  住宿 100000 × 1 页                        │
        └──────────────┬─────────────────┘
                       ▼
              合并 + 按偏好排序 + 截断
                       ▼
              SQLite 落盘（30 天 TTL）
                       ▼
         ┌─────────────┴─────────────┐
         ▼                           ▼
   喂给大模型选点                规则路径兜底
```

**为什么落盘而不是每次现查**：② 延迟不可控——一次行程要串好几个城市，几十次串行外呼，用户就盯着转圈；② 高德配额按日计量，反复问同一件事纯属浪费；③ 30 天 TTL 是折中——POI 的存续以月计，定太短是拿新鲜度换延迟，定太长会积累已停业的点。

**为什么池子里记 `origin`**：候选来自攻略库（人工整理）和高德（机器召回），可信度与粒度都不同。记下来源，才能「攻略打底、高德补长尾」，也才能在界面上如实标注。

### 三个踩过的坑

**坑一：分类白名单比错了字段，整个分类全放行。**
高德分类链形如 `科教文化服务;科研机构;科研机构`，第一段是**大类**。白名单里写「文化」去比整条链，会命中 `科教文化服务` 这个大类本身——于是 `140000` 分类**全部通过**，池子里混进「首都儿科研究所」「中国社会科学院」「北京协和医学院」。改成只比 `type_chain[1:]`（跳过大类），白名单才真正在挑具体属性。
另外补了一道**名字黑名单**（停车场、售票处、研究所、派出所…）——高德分类的是「机构属性」而非「游玩属性」，分类判不出来时，名字往往能。

**坑二：`宾馆酒店` 关键词能搜出 75 条，但多半是连锁快捷酒店。**
这是数据本身的形态，不是 bug。所以住宿额度只给 1 页 × 25 条，且截断到 8 条进提示词——每天只需要 1 条建议。

**坑三：负结果必须冷却。**
高德返回空（没覆盖 / 配额用尽 / 网络抖动）时，如果不记录，**每一个请求都会重新打一轮高德**，把配额烧光还拖慢响应。所以进程内记住「刚试过且没拿到」，10 分钟内不再重试。

## 大模型编排：约束它，然后核对它

### 不让模型自由发挥

「让 AI 规划行程」的常见做法是把需求丢给模型，让它吐一段文本或一份 JSON。问题是它会**编地名**——听起来很合理，但那个地方不存在，或者离得十万八千里。

行迹的做法是**反过来**：先把候选摆好，再用提示词约束它**只能在候选里挑**：

```
候选池（一城约 130 条）
   ├─▶ 截断成 景点 / 美食 / 住宿 三组，随行程天数动态放宽
   ├─▶ 连同城市、偏好、节奏、每天几个景点，一起发给模型
   └─▶ 要求：地名**原样照抄**，每天几个景点、主题不重复、note 20 字以内
```

但**提示词只是强烈建议，不是保证**。所以模型返回后必须核对：

```
模型返回的每一天
   ├─ 活动名在候选池里？   不在 → 丢弃
   ├─ 餐食在候选池里？     不在 → 丢弃
   ├─ 住宿在候选池里？     不在 → 丢弃（退化为「包含」匹配）
   └─ 合规率 ≥ 60%？       低于 → 整份作废，退回规则生成
```

**为什么要设「整份作废」这条线**：如果模型大部分名字都是编的，说明这次调用不可信。与其交出一份七零八落的行程，不如整个退回规则生成——至少那份是完整可用的。**静默交付半成品，比明确降级糟糕得多。**

### 一次实测驱动的契约修正

百炼的 OpenAI 兼容端点，行为与文档和直觉都不一致。这些结论都是**跑出来的**，写进代码注释以防后人凭直觉改回去：

**① `response_format=json_schema` 时，顶层声明 `type=object` 是无效的。**
连续 5 次调用，返回的顶层**永远是长度为 1 的数组** `[{...}]`——把声明的对象原样包了一层。不是偶发。把 schema 顶层改成 `array` 也不能让它「合规」，依然返回单元素数组。

**② 但嵌套结构是被严格遵守的。**
内层 `days[].activities[].name` 的字段名、类型、枚举约束都命中——说明约束解码只作用在**内层**，顶层被端点特殊处理了。

**③ `response_format=json_object` 直接 400**，要求 messages 里出现 "json" 字样。

所以做法是：**schema 照常声明成想要的形状（自文档化），解析时统一做一次「拆壳」归一化**。这比为了迎合缺陷把 schema 写成数组更可读——而且万一端点是修好了，归一化对已经是对象的结果也完全无害。

**④ 思考模式默认是开着的，而且「不传」≠「关」。**
`qwen3` 系列默认开启思考模式。实测同一请求：

| `enable_thinking` | completion_tokens | 耗时 |
|---|---|---|
| 不传该字段 | 6015 | **117 s** |
| 显式传 `false` | 大幅下降 | **18 s** |

也就是说，省下这个字段反而要付出**六倍**的延迟与 token 代价。这类「默认值陷阱」只能靠实测发现——文档里不会写。

**⑤ 提示词用拼接字符串分隔字段，模型会把整行照抄。**
第一版候选是这样给的：`"故宫博物院｜东城区｜历史/必去"`。结果模型返回的 `name` 就是**整行**：

```
"name": "故宫博物院｜东城区｜历史/必去"
```

逐一核对候选池时一条都对不上，合规率 0%，整份行程被作废。原因很清楚：**分隔符对模型不是「字段边界」，只是字符串的一部分**。改成 `{name, area, tags}` 分离字段后一次通过。
另外补了一层 `_clean_name()` 做「去装饰」级修正（截断分隔符、去书名号引号）——但**绝不猜名字**，猜出来的东西一旦进池子比对，防幻觉就形同虚设。

### 降级不是静默的

| 情况 | 行为 |
|---|---|
| 未配 `LLM_API_KEY` | 规则生成，`generator=rule`，`generator_note` 说明原因 |
| 调用超时 / 4xx | 同上，**不重试 4xx**（那是请求本身有问题，重试一百次也一样） |
| 返回不是合法 JSON | 同上 |
| 合规率 < 60% | 同上，并在 note 里给出实际合规率 |
| 单天没排出有效内容 | **只补这一天**（从候选池按游标取），不整份作废 |

结果里带 `generator`（`llm` / `rule`）与 `generator_note`，前端在标题旁标注 `✦ AI 编排` 或 `规则生成`，并在降级时把原因显示出来。

**为什么要这么较真**：静默降级是最难排查的问题——用户看到一份「好像还行」的行程，其实是规则生成的，然后得出结论「大模型就这水平」。把来源和原因显式暴露，问题一眼可见。

## 几个值得说的设计决定

**1. 打包清单用规则而不是 LLM。**
去三亚一定要泳衣、上玉龙雪山一定要氧气，这是确定性知识。用规则生成可测试、可复现、零成本零延迟。该用规则的地方硬套 LLM 是工程退步。

**2. 只允许「天内」拖拽。**
跨天拖动会让「住宿在哪、第几天在哪个城市」这些约束失效。限制范围既给自由，又不会把行程拖崩。

**3. 拖拽结果不写后端，并且在界面上明说。**
行程是生成物，手动微调属个人笔记。要做服务端持久化得引入版本号与冲突合并，那是下一阶段的事。与其假装保存，不如直说。

**4. 分享用独立 token，不复用行程 ID。**
行程 ID 顺序可猜，泄露后可被遍历。分享 token 独立随机、可撤销，撤销只删 token 不动行程。

**5. ICS 的全天事件，DTEND 是次日。**
RFC 5545 里结束时间是开区间，写成当天会导致日历少一天——这是一个很容易踩、又很难发现的坑，已写进测试。

**6. 边打边搜的请求要按序号丢弃过期响应。**
用户输入「成」时发出一次请求，接着输入「成都」又发一次。如果「成」的响应后返回，结果会被覆盖成跟关键词不匹配的旧内容——用户看到的现象是「搜错了」。每次请求领一个序号，回来时不是最新号就直接扔掉。

**7. 路线模式采纳后直接生成，不回填表单。**
用户点「按这条路线生成行程」时意图已经明确。再让他回首页看一眼表单、再点一次生成，纯属多余。

**8. 搜索结果的「有攻略 / 仅定位」是明说的，不藏着。**
有攻略的城市，行程每条都带出处；没有的城市，内容来自高德 POI。两者质量确实不同。把差别摆在选择那一刻，比让用户生成完才疑惑「怎么这条推荐得这么泛」要好得多。

**9. 大模型是「编排器」，不是「知识源」。**
开放式的「帮我规划个行程」正是模型最擅长编造的场景——它会自信地给出不存在或早已歇业的店。所以这里把它的自由度锁死：**候选由我们提供，它只负责选哪个、怎么分天、起什么主题、为什么推荐**。这样它贡献的恰好是它真正擅长的那部分（组织与表达），而事实部分仍由可控的数据源负责。

**10. 大模型生成的骨架必须由服务端把关，不能听模型报的城市。**
模型返回的 `day` / `city` 可能编号错位或缺天。行程骨架（哪天在哪座城）严格按用户选的天数分配展开，模型只负责往里填内容。否则会出现「说好 3 天北京，结果排了 4 天」。

**11. 前端按接口性质分别设超时，而不是共用一个很大的值。**
绝大多数接口是毫秒级的读写，30 秒绰绰有余；但 `/trip/generate` 要真实调大模型，5 天行程约 17 秒且随规模线性增长，用 30 秒卡它会让用户看到「请求超时」——而后端其实还在正常跑并最终会成功。所以这个接口单独放宽到 3 分钟。

**12. 等待时间长的时候，要告诉用户在等什么。**
生成要 15~20 秒，不解释的话用户会以为页面卡死了。所以提交后明确显示「正在汇集候选地点并编排逐日行程，通常需要 15–40 秒」。

## 已知边界

- 10 座城市有**完整本地攻略**（行程每条带出处）；其余城市可用高德 POI 兜底生成，内容粒度会粗一些，界面上会标出「仅定位」
- 路线推荐只在**已收录城市**里挑中途站——高德没有「哪些城市好玩」这个信息，无法对全国城市做推荐
- 出发地/目的地只接受**行政区划粒度**（省/市/区县），不接受具体景点门口
- 高德未配置 Key 时，城市搜索与实测里程不可用，自动降级为本地估算并在界面上标明
- 预算为**估算值**，不含往返大交通与购物，实际花费随季节浮动
- 门票、营业时间、预约要求**不保证实时**，出行前请以官方信息为准
- **大模型只负责「选点与编排」，不负责「提供事实」**：地名、餐食、住宿全部取自候选池并回池核对。
  它输出的 `note` 属于推荐理由，不是事实陈述——这也是不把开放问答交给它来答的原因
- 候选池的 POI 来自高德，**可能包含已停业或迁址的地点**（TTL 30 天，非实时）
- 大模型编排**不是确定性**的：同样输入两次可能得到不同排序。规则路径则是稳定可复现的
- 生成一份 5 天行程约需 15~20 秒（大模型逐字生成），城市/天数越多越慢；这是**延迟**而非卡死
- SQLite 适合单机；真上高并发需换 PostgreSQL（存储层已隔离，替换只动 `storage_service`）
